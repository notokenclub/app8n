# Architecture & Handoff

Everything needed to pick this project up cold — what exists, why it was built this way,
and where the seams are. If you're new, read this after the README.

Current state: **Phases 1–5 complete.** Typecheck and lint clean, 8/8 vault checks,
26/26 Google checks, 16/16 agent checks, production build succeeds with 13 routes.

---

## 1. What app8n is

An open-source, local-first **agentic OS** — Jarvis-style autonomous intelligence wearing
n8n's execution model, driven by natural language. You describe what you want; an agent
plans and acts against your real Google Workspace accounts; anything irreversible stops
at a human approval gate.

**Mobile (iOS + Android) is the primary interface.** The web app is a headless-decoupled
backend that the native Capacitor shell loads over a configurable URL. This is an
architectural commitment, not a future port — it is why the client talks to
`NEXT_PUBLIC_APP8N_API_URL` rather than assuming same-origin, and why OAuth returns to a
deep link instead of a redirect page.

Two invariants govern the whole design:

1. **Credential isolation.** The model never sees a raw secret. Tokens live AES-256-GCM
   encrypted in a local vault; the model names a *tool*, and a local runtime proxy
   resolves the credential and performs the call.
2. **Human-in-the-loop safety gate.** High-impact actions — external email, calendar
   mutation, document mutation — produce an interactive confirmation card with
   **Approve / Edit Parameters / Reject** before anything executes.

Both are load-bearing. A change that weakens either one is a change to the product, not
an implementation detail.

## 4. Database schema

Six tables in `src/lib/db/schema.ts`, all ownership-scoped by `user_id` with cascading
deletes. The app is single-user local-first by default, but the schema is multi-user and
queries are written that way deliberately.

**`users`** — email-unique. A single implicit local owner is seeded from
`APP8N_LOCAL_USER_EMAIL`.

**`accounts`** — one row per linked Google identity, so personal and work Workspace
accounts can coexist. Unique on `(provider, providerAccountId)`; carries granted `scopes`
as JSON and an `isPrimary` flag.

**`credential_vault`** — `secret` holds an AES-256-GCM envelope produced by
`lib/crypto/vault`. Plaintext never enters this table. Types are `google_oauth`,
`llm_api_key`, `webhook_secret`, `generic`. Carries `keyVersion` for rotation, plus
`expiresAt` and `lastUsedAt`.

**`workflows`** — `triggerType` ∈ `manual | chat | cron | webhook | gmail_poll`;
`status` ∈ `draft | active | paused | archived`; `nodesJson` / `edgesJson` for the canvas;
`isAgentic`; and `blueprintKey`, which is the idempotence key for seeding.

**`execution_logs`** — `status` ∈ `running | awaiting_approval | success | failed |
cancelled`. Two JSON columns carry the weight:

- `stepsJson` is the ordered, human-readable trace — a discriminated union `ExecutionStep`
  of `text`, `tool_call`, `tool_result`, `approval_required`, `error`.
- `messagesJson` is the model conversation as of the last step. **This is what makes a run
  resumable across an approval pause**, so a scheduled job can stop at 7am, wait for a
  human decision at lunchtime, and continue from exactly where it halted.

Note the column is `inputPayload`, not `input`. SQLite silently accepts a wrong key and
drops it, leaving a null payload — only `tsc` catches this. It has bitten us once.

**`approval_requests`** — the HITL gate, one row per decision.

- `parametersJson` is what the agent *proposed*.
- `resolvedParametersJson` is what the human actually approved after any edits, and is the
  payload the runtime executes. These being separate columns is what makes "Edit
  Parameters" real rather than cosmetic.
- `toolCallId` correlates the gate back to the exact model tool call, so a resumed run
  replays the decision against the right call rather than the next similar one.
- `status` ∈ `PENDING | APPROVED | REJECTED | EXPIRED`.

## 5. The tool registry

21 tools in `src/lib/agent/tools.ts`. Approval is **derived, not hand-maintained**:

```ts
requiresApproval: config.requiresApproval ?? config.impact === "external"
```

Every tool declares an `impact` of `read`, `write`, or `external`. Anything `external`
gates automatically, which means **adding a new outbound tool is safe by default** — you
would have to explicitly opt out to ship an ungated one. The lookup helper also fails
closed:

```ts
return TOOLS_BY_NAME[name]?.requiresApproval ?? true;
```

An unknown tool name gates rather than executes.

`docs_append_text` is the single manual override: `requiresApproval: true` despite being a
`write`, because it mutates a document someone else may be reading.

| Service | Tools |
| --- | --- |
| Gmail | `gmail_search_messages`, `gmail_get_message`, `gmail_draft_email`, **`gmail_send_email`**, `gmail_mark_read`, `gmail_archive_message` |
| Calendar | `calendar_list_events`, `calendar_find_conflicts`, **`calendar_create_event`**, **`calendar_delete_event`**, `calendar_attendance_metrics` |
| Sheets | `sheets_read_range`, `sheets_find_rows`, `sheets_append_row`, `sheets_create_spreadsheet` |
| Docs | `docs_create`, **`docs_append_text`**, `docs_read` |
| Drive | `drive_search` |
| Tasks | `tasks_list`, `tasks_create`, `tasks_complete` |

**Bold** tools are gated by the HITL approval flow.

## 6. Starter blueprints

`src/lib/blueprints.ts` holds the three shipped automations as typed data, shared by both
the seeder and the self-test — so a typo in a tool name cannot ship silently. Agent
self-test check #16 validates every step name against `AGENT_TOOLS`, asserts unique keys,
requires a real description, runs `isValidCron()` on cron blueprints, and rejects dangling
edges.

All three are `isAgentic: true`, for a stated reason: each has a step that cannot be
expressed as a fixed call — deciding which course is at risk, deciding whether an email is
really a lead. Pretending otherwise would produce a workflow that runs reliably and
answers the wrong question.

| Key | Title | Trigger | Chain |
| --- | --- | --- | --- |
| `college-debar-assistant` | College Debar & Schedule Assistant | cron `0 18 * * 1-5` | `calendar_list_events` → `calendar_attendance_metrics` → *judgement* → `tasks_create` → `gmail_draft_email` → `gmail_send_email` |
| `gmail-lead-pipeline` | Gmail Lead to Google Sheets Pipeline | `gmail_poll` | `gmail_search_messages` → `gmail_get_message` → *extract* → `sheets_find_rows` (dedupe) → `sheets_append_row` → `gmail_mark_read` |
| `daily-briefing` | Daily Calendar & Drive Briefing | cron `0 7 * * 1-5` | `calendar_list_events` → `calendar_find_conflicts` → `drive_search` → `gmail_search_messages` → `docs_create` |

*Italic* steps have no `tool` — they are the judgement the agent is there to supply.

**Seeder idempotence.** `scripts/seed-blueprints.ts` upserts on `(userId, blueprintKey)`.
Re-running refreshes the definition — title, description, steps, trigger — but
deliberately leaves `status` alone, so a blueprint someone paused stays paused instead of
quietly resuming itself. Pass `--reset` to also restore the shipped status.

## 7. Design note: making `isAgentic` mean something

`is_agentic` shipped as a **dead flag**. It existed in the schema, the migration, the API
response and the `WorkflowSummary` type — and nothing read it. Worse, `/workflows` was
drawing a step diagram the running agent had never seen: the canvas showed what the
automation supposedly does, while the run only ever received the description string.

Seeding it "correctly" would have been theatre, so it was fixed in both directions.

`src/lib/scheduler/worker.ts` now renders `nodesJson` into the run instruction, worded
*by* the flag:

- agentic — *"This is the plan it usually takes. Follow it where it fits and deviate where
  the situation calls for it."*
- fixed — *"Carry out these steps in order. Do not add steps or skip one unless it
  genuinely cannot be completed."*

`gmail_poll` workflows additionally get: only consider messages that arrived since the
last run; if there is nothing new, say so and stop.

`workflow-list.tsx` surfaces an Agentic / Fixed-steps indicator so the distinction is
visible where people actually look.

The general lesson, worth keeping: a column that nothing reads is not a feature, and a
diagram the runtime has never seen is a lie.

## 8. Commands

```bash
npm run dev                 # Next dev + Turbopack
npm run worker              # background scheduler — separate process, decoupled by design
npm run seed:blueprints     # install the three starter automations (idempotent)
npm run seed:demo           # one pending gmail_send_email approval, for UI work

npm run typecheck
npm run lint
npm run vault:selftest      # 8 checks
npm run google:selftest     # 26 checks
npm run agent:selftest      # 16 checks

npm run db:generate | db:migrate | db:push | db:studio
npm run vault:keygen        # mint APP8N_ENCRYPTION_KEY

npm run cap:sync
npm run cap:add:ios | cap:add:android | cap:open:ios | cap:open:android
```

Scripts use **relative** imports (`../src/lib/db`), not the `@/` alias — the alias is not
resolved when they run under `tsx`. Type-only imports are the exception, since `import
type` is erased before it matters.

## 9. Environment

Full annotated list lives in `.env.example`. The ones that trip people up:

| Variable | Note |
| --- | --- |
| `APP8N_ENCRYPTION_KEY` | Vault master key, from `npm run vault:keygen`. Root of trust — lose it and every stored credential is unrecoverable. There is no backdoor, by design. |
| `APP8N_MOCK_GOOGLE=1` | Swaps the Google clients for in-memory fixtures. Every connector and blueprint runs with **no credentials and no network**. This is how you develop without a Cloud project, and how CI runs. |
| `APP8N_SERVER_URL` | The backend the native shell loads, read at `cap sync` time. On a real device use your machine's LAN IP — `localhost` resolves to the phone. |
| `NEXT_PUBLIC_APP8N_API_URL` | Backend the client calls. Leave blank for same-origin web; set it for the native shell. |
| `APP8N_MOBILE_REDIRECT_URI` | `app8n://auth/callback`. Must match the URL scheme registered in the iOS and Android projects or OAuth will complete and then strand the user. |
| `DATABASE_URL` | `file:./data/app8n.db` locally; point at Postgres/Supabase for server mode. |

`.env.local` and `data/app8n.db` are gitignored. `.env.example` contains only placeholders
and localhost URLs.

## 10. Contributing workflow

`main` is a **protected branch**. Pushing to it directly will be refused regardless of how
in-sync you are. Every change goes through a branch and a pull request:

```bash
git switch -c feat/whatever
# work, commit
git push -u origin feat/whatever   # then open the PR
```

Before opening a PR, the full gate is:

```bash
npm run typecheck && npm run lint && \
npm run vault:selftest && npm run google:selftest && npm run agent:selftest && \
npm run build
```

## 11. Where to pick up

Phases 1–5 are done. Roughly in order of value:

1. **Real Google credentials end-to-end.** Everything so far is verified against
   `APP8N_MOCK_GOOGLE=1`. The OAuth flow, refresh-token handling and scope consent have
   not yet met a live Workspace account.
2. **Native builds.** Capacitor configuration is written, but the iOS and Android projects
   are not generated or committed, and the `app8n://` scheme still needs registering in
   both.
3. **Execution history UI.** `stepsJson` captures a rich trace that nothing currently
   renders — there is no run-history view at all.
4. **Workflow authoring.** The canvas is read-only. Turning a chat into a saved automation
   ("make that a daily thing") is the headline feature still missing.
5. **Approval expiry.** `expiresAt` exists on `approval_requests`; nothing sweeps it, so a
   `PENDING` gate lives forever.
6. **Push notifications.** `@capacitor/push-notifications` is installed but unwired. It is
   the natural delivery channel for an approval gate that fires at 7am.
